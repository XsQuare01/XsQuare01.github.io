# 증명 의무·원문 충실도(L6) 판정 지침 정립 (설계)

- 날짜: 2026-08-18
- 상태: 승인됨 (사용자 확인)
- 이슈: #88 (증명 의무·원문 충실도(L6) 판정 지침 정립)
- 선행: #46·#52 논증 가시화, #86 정본 통합, #87 루브릭 정본 단일화, #92 읽힘 가이드
- 브랜치: `docs/proof-obligation-l6-guidance`

## 목표

작성자와 리뷰어가 **같은 기준으로** 증명 의무와 원문 충실도를 판단하게 만든다. 지금은 두 축이 다 비어 있다. 작성자 정본은 증명 모듈을 "명제·전제·추론 단계·결론을 구분한다" 두 줄로만 규정하고, 리뷰 루브릭은 L7에서 MECE와 base·step만 언급한다. "적용 영역", "한정사", "비용 모델", "점화식", "비재귀 작업", "유일성·존재성·완전성·건전성" 같은 판단 단위가 저장소 문서에 한 번도 등장하지 않는다.

L6는 더 좁은 문제가 아니라 판정 의미가 흔들리는 문제다. 2026-08-13 전수 리뷰는 "Notion 원문을 대조할 수 없었다"를 59개 글 전부 `severity: 🟢 / gate_effect: info`로 기록했다. 검증하지 못한 상태가 검증 통과와 같은 색으로 보고된 것이다. 이 설계는 그 상태를 이름 있는 네 갈래로 나누고 각각의 severity와 gate 동작을 고정한다.

## 결정 (브레인스토밍 확정)

- **L6 severity — L6만 coverage row 예외로 둔다.** 커맨드 문서는 문제 없는 범주의 coverage row를 `🟢 / info`로 고정하지만, L6는 원문 대조 실패가 "이슈 없음"이 아니라 "검증 미완료"다. L6 coverage row는 상태에 따라 severity가 갈린다고 명시한다. `source unavailable`은 `🟡 / warn`이다. 게이트는 warn이므로 통과하되 미완료 사실이 리포트에 남는다. `l6_state` 같은 신규 필드는 만들지 않는다 — 스키마 v3 승격은 이슈 비범위인 serializer 구현을 부른다.
- **지침 배치 — `docs/writing-rules.md` 정본을 확장한다.** 새 문서를 만들지 않는다. 루브릭이 이미 "상세 체크리스트는 정본에 있으므로 여기서 복제하지 않는다"고 선언해 단일 정본을 가리키므로, 증명 의무 표와 비용 모델 기준의 집은 정본이다. 루브릭은 L6·L7 **판정 기준**만 담고 정본을 가리킨다. 정본/읽힘 2축 구조를 유지한다.
- **표류 방지 — 계약 테스트를 추가한다.** 저장소는 이미 루브릭 문서와 코드를 `test_canonical_rubric_*`로 묶어 둘이 어긋나면 실패시킨다. 같은 패턴으로 새 규약도 박는다. 문서 정합성 테스트는 이슈가 배제한 strict gate·serializer 구현에 해당하지 않는다.
- **소급 적용 없음.** `docs/reviews/README.md`가 "지적을 나중에 고쳤어도 finding 행은 그 시점 근거로 남긴다"를 규약으로 두므로, 과거 리포트의 L6 행을 고쳐 쓰지 않는다. 새 L6 규약은 적용 시점을 문서에 명시하고 이후 생성 리포트부터 적용한다.
- **범주를 늘리지 않는다.** 5개 표현 정렬을 새 범주 L8로 만들지 않고 기존 L4를 넓힌다. 근거는 아래 「범주를 늘리지 않는 이유」.

## 범주를 늘리지 않는 이유

이슈 완료기준 4번은 본문·수식·의사코드·worked example·SVG 정렬 체크리스트를 요구한다. 새 범주(L8)로 만들면 `REQUIRED_LLM_RULES`가 8개가 되고, 기존 리포트에는 L8 coverage row가 없으므로 게이트 대상 31개가 즉시 `exit 2`가 된다. 전수 재리뷰를 강제하는 변경이다.

대신 L4를 **「표현 정렬 — SVG·의사코드·수식·계산 예시 ↔ 본문」**으로 넓힌다. `rule_id`는 `L4`로 유지되므로 과거 coverage row가 그대로 유효하다. L4는 원래 "SVG의 레이블·수치가 본문 주장과 맞는지"였고, 정렬 대상을 SVG에서 네 표현으로 넓히는 것은 같은 판정의 확장이다.

## `writing-rules.md` 구성

### 1단계 원문 확인 — 투명 확장 기준

추가를 일률적으로 금지하지 않는다. 세 조건을 모두 지키면 허용한다: ① 추가임을 provenance에 밝힌다 ② 승인된 포스트별 스펙과 충돌하지 않는다 ③ 원문의 구조·논증 흐름·의도를 보존한다. 하나라도 어기면 승인을 받기 전까지 넣지 않는다.

### 2단계 글 설계 — 주장 표식과 의무 도출

핵심 주장에서 강한 한정사(모든·유일한·정확히 한 번·항상·최적)를 표시하고, 각 주장이 만드는 증명 의무를 설계 단계에 적는다. 의무를 닫을 자리가 본문 구조에 없으면 주장을 약하게 고치거나 절을 만든다.

4단계가 아니라 2단계에 두는 이유가 있다. 검증 준비 단계에서 의무를 처음 발견하면 초안이 이미 그 논증 없이 쓰인 상태이고, 그때의 수정은 문단 삽입이 아니라 구조 변경이 된다.

### 4단계 증명 모듈 — 2항에서 6항으로

기존 2항을 유지하고 넷을 더한다.

- 가정, 적용 영역(주장이 성립하는 입력과 조건의 범위), 사용한 기호의 정의를 증명 앞에 모은다.
- 표기와 한정사가 문단·수식·의사코드 사이에서 같은 뜻으로 쓰이는지 문서 전체에서 대조한다.
- 경우 구분이 상호 배타적이고 전체를 포괄하는지(MECE) 확인하고, 귀납은 base와 step을 나눠 각각 닫는다.
- 경계값·빈 입력·최소 크기·중복값·동일값처럼 그 문제의 퇴화 사례를 다루거나, 다루지 않아도 되는 이유를 적는다.
- 직관 설명과 증명을 구분해 표시하고 직관을 증명 자리에 두지 않는다.

### 증명 모듈 안 「강한 주장과 증명 의무」 표

| 주장 형태 | 생기는 의무 | 닫는 방법 |
|---|---|---|
| 모든 …에 대해 성립한다 | 완전성 | 임의 원소를 잡아 논증하거나 구조적 귀납으로 전 범위를 덮는다 |
| …만이 / …인 경우에만 | 건전성과 역방향 | 양방향을 각각 증명하거나 필요조건과 충분조건을 나눠 적는다 |
| 유일하다 | 유일성 | 서로 다른 둘을 가정해 같음을 유도한다 |
| 존재한다 / 항상 찾는다 | 존재성 | 구성해 보이거나 비존재 가정에서 모순을 얻는다 |
| 정확히 한 번 …한다 | 존재성과 중복 배제 | 최소 한 번과 두 번 이상 불가를 각각 닫는다 |
| 최적이다 | 최적성 | 임의 해와 비교하거나 교환 논증으로 손실 없음을 보인다 |
| 종료한다 | 종료성 | 단계마다 감소하는 정수 척도를 제시한다 |

이슈가 요구한 "예시와 함께"는 기존 「진단용 전후 사례」 패턴을 이어 **사례 4 — 의무를 열고 닫지 않은 증명 문단**으로 붙인다. 사례 1~3과 같은 전후 대조 형식을 쓴다.

### 4단계 복잡도 모듈 — 3항 추가

- 비용 모델을 밝힌다. 무엇을 1 연산으로 세는지, 입력 크기 기호가 무엇인지, 어떤 계산 모델을 쓰는지 적는다.
- 재귀 알고리즘은 점화식의 각 항이 무엇을 세는지와 기저 조건을 검증한다.
- 재귀 호출 밖의 작업은 **비재귀 작업**으로 부르고 결합·분할·순회 중 무엇인지 밝힌다. "나머지", "기타" 같은 모호한 이름을 쓰지 않는다.

### 4단계 「표현 정렬 모듈」 신설

- 본문 설명·수식·의사코드·계산 예시·SVG가 같은 전제, 같은 실행 순서, 같은 값, 같은 결론을 말하는지 대조한다.
- 한 표현을 고쳤으면 나머지 표현에 같은 수정이 필요한지 확인하고, 확인한 표현을 리뷰 인계에 적는다.
- 그 글에 없는 표현은 다른 비보편 모듈과 같이 `N/A — 해당 요소 없음`으로 남긴다.

## `review-rubric.md` 구성

### L4 — 표현 정렬

이름과 범위를 「표현 정렬 — SVG·의사코드·수식·계산 예시 ↔ 본문」으로 넓힌다. SVG 레이블·수치 확인은 그대로 두고, 의사코드와 본문 설명의 실행 순서 차이, 수식과 계산 예시의 값 차이도 같은 범주로 판정한다. 상세 대조 절차는 정본의 표현 정렬 모듈을 가리킨다.

### L6 — 네 상태

상태는 넷이다. `actual mismatch`만 불일치의 깊이에 따라 severity가 두 갈래로 갈리므로 표는 다섯 행이 된다. 상태 이름은 넷을 그대로 쓰고 국소·핵심은 같은 상태의 등급으로 적는다.

| 상태 | 뜻 | severity | gate_effect |
|---|---|---|---|
| verified fidelity | 원문 또는 승인 자료를 실제로 대조해 구조·핵심 주장·논증 흐름·의도 보존을 확인 | 🟢 | info |
| approved/transparent extension | 원문 밖 내용이 있으나 provenance에 밝혀져 있고 승인 스펙에 부합하며 의도와 논증을 훼손하지 않음 | 🟢 | info |
| source unavailable | 원문이나 승인 자료에 접근할 수 없어 충실도를 검증하지 못함 | 🟡 | warn |
| actual mismatch — 국소 | 대조 가능한 자료와 사소한 표현 차이 | 🟡 | warn |
| actual mismatch — 핵심 | 구조·주장·증명 흐름·의도·사실 관계를 바꾸는 불일치 | 🔴 | fail |

규칙 세 줄을 함께 둔다.

- 상태 이름을 `message` 맨 앞에 적어 리포트끼리 비교할 수 있게 한다.
- 원문 접근 실패를 verified fidelity로 적지 않는다. `source unavailable`은 자동 차단하지 않지만 L6 검증은 미완료로 남는다.
- 원문 밖 추가 자체를 불일치로 판정하지 않는다. 판정 대상은 투명성·승인·의도 보존 세 조건이다.

L6 coverage row는 `🟢 / info` 고정에서 제외한다고 명시하고, 이 규약이 2026-08-18 이후 생성 리포트에 적용된다고 적는다.

### L7 — 5줄로 확장

계산 예시가 주장한 값으로 실제 계산되는가 / 복잡도 주장에 비용 모델이 밝혀져 있고 알고리즘과 맞는가 / 재귀는 점화식의 항과 기저가 검증되었는가 / 강한 주장이 만든 증명 의무가 논증으로 닫혔는가(MECE·base·step·퇴화 사례 포함) / 직관을 형식적 증명 자리에 세우지 않았는가. 판단 단위의 정의는 정본의 증명 의무 표를 가리킨다.

## `reviews/README.md` 구성

- severity↔gate_effect 표 뒤에 L6 예외 절을 둔다. 3단 매핑은 유지하되, L6는 상태가 severity를 정한다는 점과 `source unavailable`이 coverage row이면서 `🟡 / warn`인 이유를 적는다.
- 보고 예시 두 개를 넣는다. `source unavailable`(🟡)과 `verified fidelity`(🟢). 이슈 완료기준 5번의 "일관된 보고 예시"가 이것이다.
- 검사 항목 요약의 L4·L6·L7 라벨을 루브릭과 일치시킨다. 계약 테스트가 둘을 대조하므로 동시에 고쳐야 한다.
- 면제 규칙 절에 L6 상태 규약의 적용 시점을 기록한다.

## 커맨드 문서 구성

`review-post.md`와 `review-post-all.md`의 coverage row 규정에 같은 문단을 넣는다. L6는 상태에 따라 severity가 갈리며, 원문 대조 실패를 `검토 완료, 이슈 없음`으로 적지 않고 상태 이름과 근거를 적는다.

## 검증 / DoD
