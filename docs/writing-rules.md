# 블로그 작성 정본 가이드

이 문서는 블로그 포스트의 원문 확인부터 리뷰 인계까지 적용하는 단일 정본이다. 새 글을 쓰거나 기존 글을 고칠 때 구조, 문체, provenance 분류, 기술 검증 준비를 한 흐름으로 관리한다. 문장 퇴고만 다루지 않으며, `review-post`의 L1 문체 검사도 이 문서의 문장 규칙을 기준으로 삼는다.

이 문서는 "틀리지 않는 글"(정확성·구조·검증)을 다룬다. "잘 읽히는 글"(몰입·읽힘)의 진단 렌즈는 동반 문서 [`readability-guide.md`](./readability-guide.md)에 있으며, 강제 계약이 아니라 참고용이다.

## 권한과 책임

### 권한 순서

1. **`AGENTS.md` 원문 보존 규칙은 비가역적이며 재정의할 수 없다.** Notion 원문의 핵심 줄기, 기본 구조, 증명/논증 흐름, 의도한 주장을 보존한다. 문장 다듬기와 오류 수정도 이 범위를 침범할 수 없다.
2. **이 정본 가이드는 기본 workflow다.** 별도 지시가 없다면 모든 포스트 작성과 수정에 이 순서와 확인 항목을 적용한다.
3. **포스트별 스펙은 구조 기본값만 달리 정할 수 있다.** 원문 특성 때문에 절 순서나 설명 배치를 바꿀 수 있지만, 예외 범위와 사유를 포스트별 스펙에 기록해야 한다. 원문 보존 규칙이나 사실 정확성 기준은 예외로 만들 수 없다.

### 작성자 책임

- 글의 구조와 문체를 설계하고 초안과 퇴고를 수행한다.
- 각 내용의 provenance를 원문, 승인된 추가, 작성 중 확인이 필요한 추가로 분류한다.
- 사실, 수식, 증명, 코드, SVG, 계산 예시, 복잡도를 리뷰어가 검증할 수 있도록 근거와 재현 절차를 준비한다.
- provenance 표지는 포스트별 스펙 또는 리뷰 인계물에 기록한다. 게시되는 포스트 본문에는 원문/추가 라벨을 붙이지 않으며, 원문의 존재 자체도 드러내지 않는다. 3단계의 「원문을 본문에서 드러내지 않는다」를 따른다.
- 작성자는 검증 자료를 준비하지만 정확성이나 증명 타당성을 스스로 최종 판정하지 않는다.

### 리뷰 책임

- 원문 충실성과 승인 범위를 확인한다.
- 사실 및 기술적 정확성을 판정한다.
- 증명의 전제, 논리 전개, 결론이 타당한지 판정한다.

## 6단계 작성 workflow

모든 단계의 `공통 필수`는 포스트 종류와 관계없이 적용한다. 증명, 코드, SVG, 계산 예시, 복잡도 모듈은 해당 요소가 있을 때만 적용한다.

### 1. 원문 확인

#### 공통 필수

- [ ] Notion 원문, 사용자 제공 자료, 포스트별 스펙처럼 승인된 원천을 확인하고 원문의 핵심 줄기, 기본 구조, 증명/논증 흐름, 의도한 주장을 기록한다.
- [ ] **본문을 작성하기 전에 사용자에게 예상 독자의 지식 수준과 읽는 목적을 묻는다.** 답은 포스트별 스펙이나 작업 메모에 기록하며, 완성된 글에서 사후 추정한 독자상을 사용자의 의도로 확정하지 않는다.
- [ ] 기존 글은 현재 저장소 글과 원문을 대조하고, 바꾸지 말아야 할 구조와 논지를 표시한다.
- [ ] 원문, 명시적으로 승인된 추가, 확인이 필요한 추가를 구분해 포스트별 스펙이나 작업 메모에 provenance를 기록한다.
- [ ] **신규 글에서 원문을 확인할 수 없으면 명시적으로 승인된 자료와 범위를 넘는 작성을 중단한다.** 추측으로 구조, 주장, 예시를 보충하지 않는다.
- [ ] **기존 글에서 Notion 원문을 확인할 수 없으면 `AGENTS.md`에 따라 저장소에 있는 현재 글의 구조와 논지를 기준으로 보존한다.** 이 fallback은 신규 글의 승인 범위를 넓히지 않는다.

### 2. 글 설계

#### 공통 필수

- [ ] 글의 질문, 답, 답을 지지할 정의, 근거, 증명 순서를 먼저 세운다.
- [ ] 각 절과 문단의 역할을 정의, 예시, 반례, 증명 단계, 해석 중 하나로 정하고 앞뒤 이동 경로를 확인한다.
- [ ] 포스트별 스펙이 정본의 구조 기본값과 다르면 예외 범위와 원문에 맞춰 달라져야 하는 사유를 스펙에 기록한다.
- [ ] 처음 읽는 독자에게 필요한 용어, 기호, 전제를 도입 순서에 배치한다.

#### 글을 세우는 규칙

이 절은 글의 구조를 세울 때 쓰는 실무 지침이다. 본편과 후속 글을 나누는 기준과, 문단의 결함을 찾는 진단용 사례를 둔다.

##### 본편과 후속 글의 경계

- [ ] **중심 주장에 필수인 재료는 본편에 둔다.** 정의, 핵심 알고리즘, 필요한 증명, 중심 결론은 길어지더라도 본편에서 빼지 않는다.
- [ ] **후속 글은 독립 완결성을 기준으로 나눈다.** 중심 결론에 필수적이지 않은 내용이 독립된 질문, 논증 또는 구현을 갖고, 그 글만으로 이해할 수 있으며, 본편에서 링크로 관계를 설명할 수 있을 때만 분리한다.
- [ ] **길이만으로 나누지 않는다.** 글자 수나 분량은 분리 판단의 단독 기준이 아니다. 짧아도 독립된 질문이면 후속 글이 될 수 있고, 길어도 중심 주장에 필요한 내용이면 본편에 남긴다.

##### 진단용 전후 사례

아래 세 사례는 문단의 결함을 찾고 수정 방향을 정하는 진단 기준이다. 고정된 제목, 문장 수, 문단 순서나 모든 글에 통용되는 윤곽을 제시하지 않으며, 고정 템플릿을 요구하지 않는다. 실제 수정에서는 원문의 구조와 의도를 보존하고 문맥에 맞는 표현을 고른다.

###### 사례 1. 개념 설명 문단

**수정 전**

선택 정렬은 효율적으로 가장 작은 값을 찾아 정렬한다.

**결함:**

'효율적으로'라는 평가만 있고, 무엇을 반복해 어떤 결과가 생기는지 보이지 않는다.

**수정 후**

선택 정렬은 인덱스 $i$마다 아직 정렬하지 않은 구간에서 최솟값을 한 번 찾고 $i$번째 원소와 바꾼다. 이 동작을 반복하면 정렬된 앞 구간이 한 칸씩 늘어나며, 최솟값 비교 횟수는 $(n-1)+(n-2)+\cdots+1$이므로 입력 크기에 대해 $O(n^2)$이다.

**개선 이유:**

반복 대상인 미정렬 구간, 최솟값 탐색과 교환이라는 동작, 정렬 구간과 비교 횟수라는 관찰 가능한 결과를 이름 붙여 막연한 평가를 확인 가능한 설명으로 바꿨다.

###### 사례 2. 증명 진행 문단

**수정 전**

가장 빨리 끝나는 일을 고르면 남은 시간이 가장 많으므로 이 방법은 최적이다.

**결함:**

직관에서 최적성으로 바로 넘어가며, 비교할 해와 교환 뒤에도 해가 유지되는 이유가 드러나지 않는다.

**수정 후**

greedy 해 $A$는 현재까지 공통으로 선택한 prefix 뒤에서 그 prefix와 호환되는 남은 일 중 종료 시간이 가장 빠른 일을 반복해 고른다고 하자. 최적해 $O$의 일을 시간 순서로 놓고 두 해가 처음 달라지는 자리에서 $A$의 선택을 $g$, $O$의 선택을 $o$라 하자. $g$와 $o$는 모두 공통 prefix와 호환되는 후보이고 $g$가 가장 빨리 끝나므로 $finish(g) \le finish(o)$다. $O$에서 $o$를 $g$로 바꾸면 공통 prefix와 선택한 일의 수가 보존된다. $O$에서 $o$ 뒤의 모든 일은 $o$가 끝난 뒤 시작하고 $g$는 $o$보다 늦게 끝나지 않으므로, 이후 일도 모두 $g$와 호환된다. 이 교환으로 얻은 해도 최적이며, 다음 차이에서도 같은 교환을 반복하면 $A$와 일치하는 최적해를 얻는다.

**개선 이유:**

공통 prefix, 두 호환 후보 $g$와 $o$, earliest-finish 선택에서 나오는 종료 시간 부등식, prefix·선택 수·후속 호환성의 보존을 드러내 반복 교환의 근거를 세웠다. 이는 증명 전개의 수정 방향일 뿐이며, 증명 의무 전체를 정하거나 타당성을 대신 판정하지 않는다.

###### 사례 3. 코드 및 예시 설명 문단

**수정 전**

`partition`을 호출해 한쪽만 재귀하므로 quickselect는 항상 $O(n)$이다.

**결함:**

함수의 반환값과 배열 상태가 제어 흐름에 어떻게 쓰이는지 없고, 재귀 구간의 크기 조건 없이 선형 복잡도를 단정한다.

**수정 후**

`partition(A)`은 배열을 pivot 기준으로 재배치하고 pivot의 최종 인덱스 $p$를 반환한다. 찾는 인덱스 $k$가 $p$보다 작으면 왼쪽 구간, 크면 오른쪽 구간만 재귀하며, 같으면 `A[p]`를 반환한다. 각 단계에서 남는 구간이 어떤 고정된 $\alpha<1$에 대해 최대 $\alpha n$이라는 조건이 있으면 $T(n)\le T(\alpha n)+cn=O(n)$이다. 이 균형 조건이 없으면 한쪽만 재귀한다는 사실만으로 항상 선형이라고 할 수 없으며 최악에는 $O(n^2)$이 될 수 있다.

**개선 이유:**

반환 인덱스와 변경된 배열 상태를 분기 및 반환에 연결하고, 선형 복잡도가 성립하는 조건과 성립하지 않는 경우를 함께 밝혔다. 코드의 실제 동작과 복잡도 판정은 별도 검증 자료를 바탕으로 리뷰에서 확정한다.

이 사례들은 독립적인 작성과 리뷰 판단을 돕는 진단 방향이다. 사례의 표현을 그대로 복사하거나 모든 개념, 증명, 코드 문단을 같은 순서로 맞추지 않는다.

### 3. 초안

#### 공통 필수

- [ ] 승인된 범위 안에서 주장과 근거를 끝까지 적고, 정의와 기호를 처음 쓰는 곳에서 설명한다.
- [ ] 쓰는 동안 발견한 빈틈, 모순, 출처 불명 내용은 숨기지 말고 포스트별 스펙이나 리뷰 인계물에 남긴다.
- [ ] 내용, 구조, 문장 퇴고를 섞지 않는다. 초안에서는 논증을 완성하고 다음 단계에서 검증 자료를 준비한다.
- [ ] 아래 「원문을 본문에서 드러내지 않는다」를 적용한다.

#### 원문을 본문에서 드러내지 않는다

게시 본문은 Notion 원문이나 강의 노트 같은 **비공개 원천의 존재를 드러내지 않는다.** 원천을 가리키는 서술과 그 원천에서 인용했다는 표시가 모두 대상이다.

**대상이 되는 서술**

- 원천을 주어로 삼는 문장: "원문 노트는 …라고 적었다", "강의 노트는 이 둘을 …이라 부른다"
- 원천 대비 범위를 밝히는 문장: "여기서부터는 강의 노트 밖 확장이다", "이 글은 강의 노트 밖 확장으로 …"
- 원천의 상태를 전하는 문장: "원문 노트가 …라고 남긴 방법인데"

**이유**

독자에게 그 원천은 존재하지 않는 자료다. 본문이 원천을 가리키면 독자가 확인할 수 없는 출처를 만들고, 글이 스스로 세워야 할 근거를 밖으로 넘긴다. provenance는 「작성자 책임」이 정한 대로 포스트별 스펙과 리뷰 인계물이 맡는다. 본문은 근거를 본문 안에서 세운다.

**대신 하는 일**

귀속만 걷고 내용은 살린다. 원천이 남긴 표현이 설명에 도움이 되면 작성자의 서술로 다시 적는다. 원천 대비 범위를 밝히던 문장은 삭제하거나, 독자가 실제로 쓸 수 있는 정보(다음 글 링크, 다루는 질문)로 바꾼다. 문장을 걷어내며 논증 단계나 조건이 함께 사라지지 않게 한다. 이 규칙은 표현을 다루며 `AGENTS.md`의 원문 보존 범위를 넓히거나 좁히지 않는다.

**적용하지 않는 경우**

공개된 외부 문헌은 대상이 아니다. 논문, 교과서, URL처럼 독자가 직접 확인할 수 있는 출처는 밝히는 편이 낫고, 「인용과 귀속 주의」의 기준을 따른다. 구분 기준은 원천이 비공개냐가 아니라 **독자가 확인할 수 있느냐**다.

**진단용 전후 사례**

| 수정 전 | 수정 후 |
| --- | --- |
| 강의 노트는 이 둘을 "$a_i$ 를 포함하는 최선"과 "포함하지 않는 최선"이라 부른다. | 이 둘을 "$a_i$ 를 포함하는 최선"과 "포함하지 않는 최선"이라 부르기도 한다. |
| 원문 노트가 "사실 이게 답이 되는지는 모르겠다"고 남긴 방법인데, 위 두 줄이 그 근거다. | 이 방법이 정말 답을 내는지는 의심스러울 수 있는데, 위 두 줄이 그 근거다. |
| 여기서부터는 강의 노트 밖 확장이다. | (삭제) |

**검출 보조 (참고용, 삭제는 문맥 판단)**

```bash
grep -nE '(원문|원본|강의) ?노트|원문에서는|노트 밖' <파일>
```

### 4. 기술 검증 준비

#### 공통 필수

- [ ] 사실 주장, 전문 용어, 외부 인용의 출처와 확인 위치를 리뷰어가 따라갈 수 있게 정리한다.
- [ ] 수정 전후 의미가 달라진 곳과 원문의 의도에서 벗어날 수 있는 곳을 표시한다.
- [ ] 실행 가능한 검증 명령, 필요한 입력, 기대 결과를 준비하고 실행하지 못한 항목은 이유를 기록한다.
- [ ] 작성자는 검증 가능성을 준비하며, 사실 및 기술 정확성과 증명 타당성의 최종 판정은 리뷰에 맡긴다.

#### 해당할 때만 확인하는 비보편 모듈

아래 모듈은 모든 글에 강제하지 않는다. 포스트에 요소가 있으면 해당 모듈을 준비하고, 없으면 리뷰 인계에서 `N/A — 해당 요소 없음`처럼 미적용 사유를 기록한다.

##### 증명 모듈

- [ ] 증명할 명제, 전제, 사용한 정의와 정리, 각 추론 단계, 결론을 구분한다.
- [ ] 생략한 단계와 외부 정리의 출처를 표시해 리뷰어가 타당성을 판정할 수 있게 한다.
- [ ] 가정, 적용 영역, 사용한 기호의 정의를 증명 앞에 모은다. 적용 영역은 주장이 성립하는 입력과 조건의 범위다.
- [ ] 표기와 한정사가 문단, 수식, 의사코드 사이에서 같은 뜻으로 쓰이는지 문서 전체에서 대조한다.
- [ ] 경우 구분이 상호 배타적이고 전체를 포괄하는지(MECE) 확인하고, 귀납 논증은 base와 step을 나눠 각각 닫는다.
- [ ] 경계값, 빈 입력, 최소 크기, 중복값, 동일값처럼 그 문제의 퇴화 사례를 다루거나 다루지 않아도 되는 이유를 적는다.
- [ ] 직관 설명과 증명을 구분해 표시하고 직관을 증명 자리에 두지 않는다.
- [ ] 강한 주장마다 아래 표로 의무를 도출하고 각 의무를 닫은 위치를 리뷰 인계에 적는다.

###### 강한 주장과 증명 의무

강한 한정사는 그 자체로 증명 의무를 만든다. 주장을 약하게 고치는 것도 의무를 닫는 방법이다.

| 주장 형태 | 생기는 의무 | 닫는 방법 |
|---|---|---|
| 모든 …에 대해 성립한다 | 완전성 | 임의 원소를 잡아 논증하거나 구조적 귀납으로 전 범위를 덮는다 |
| …만이 / …인 경우에만 | 건전성과 역방향 | 양방향을 각각 증명하거나 필요조건과 충분조건을 나눠 적는다 |
| 유일하다 | 유일성 | 서로 다른 둘을 가정해 같음을 유도한다 |
| 존재한다 / 항상 찾는다 | 존재성 | 구성해 보이거나 비존재 가정에서 모순을 얻는다 |
| 정확히 한 번 …한다 | 존재성과 중복 배제 | 최소 한 번과 두 번 이상 불가를 각각 닫는다 |
| 최적이다 | 최적성 | 임의 해와 비교하거나 교환 논증으로 손실 없음을 보인다 |
| 종료한다 | 종료성 | 0 이상인 정수 척도가 매 단계 감소함을 보인다 |

##### 코드 모듈

- [ ] 코드의 실행 환경, 입력, 실행 명령, 기대 출력을 기록한다.
- [ ] 본문의 설명과 코드가 같은 동작, 경계 조건, 복잡도를 말하는지 대조할 자료를 준비한다.

##### SVG 모듈

- [ ] SVG의 텍스트, 화살표, 기호, 색상 의미가 본문 설명과 일치하는지 대조한다.
- [ ] 파일 경로, 구조 검사 결과, 필요한 시각 확인 절차를 리뷰 인계에 포함한다.

##### 계산 예시 모듈

- [ ] 입력값, 중간 계산, 최종 결과를 적어 독립적으로 재계산할 수 있게 한다.
- [ ] 반올림, 단위, 인덱스 기준처럼 결과에 영향을 주는 조건을 명시한다.

##### 복잡도 모듈

- [ ] 입력 크기와 계산 모델을 정의하고 시간 및 공간 복잡도의 유도 근거를 적는다.
- [ ] 최악, 평균, 상환 분석 중 어느 기준인지 밝히고 코드 설명과 일치하는지 확인할 자료를 준비한다.

### 5. 문장 퇴고

#### 공통 필수

- [ ] 사실, 구조, 검증 준비를 먼저 마친 뒤 아래 대원칙과 문장 체크리스트를 적용한다.
- [ ] 짧게 쓰기 위해 조건, 논증 단계, 재현에 필요한 코드, 안정된 용어를 삭제하지 않는다.
- [ ] 기계 검출 결과는 후보로만 사용하고 문맥에 따라 남길 표현을 판단한다.

#### 대원칙

- **과형식화·과교정 금지.** 의미·수식·코드·용어·직관 설명의 자연스러움은 건드리지 않는다. 문체만 조인다.
- **강박 금지.** 접속어를 0으로 만들거나 '것/의'를 전부 없애려 하지 않는다. 논리 전환에 꼭 필요한 것은 남긴다. 목적은 명료함이지 획일화가 아니다.
- **기술적 정확성 우선.** 아래 문학적 조언은 수학적 정확성, 안정된 용어, 출처와 증명 구조, 수식, 코드, 자연스러운 한국어보다 앞서지 않는다. 짧게 쓰려다 조건이나 논증 단계를 없애지 않는다.
- **문장 배열이 의미를 바꾸지 않게.** 문장을 짧게 쪼개거나 어순을 바꿀 때 조건은 결론 가까이에, 원인과 결과는 대응하는 자리에 두어 조건·인과 관계가 뒤틀리지 않게 한다. 이는 문체가 아니라 정확성 문제다.
- 코드 주석·인용·수식 내부 텍스트는 대상이 아니다.

#### 군더더기 없애기

- [ ] **접속어 최소화 (최우선).** 문두의 '그리고·그런데·그러나·따라서·하지만·그래서·그러니' 남발을 자제한다. 문장 순서·인과로 대체하거나 삭제한다. 접속어는 글의 긴장감을 떨어뜨린다. *(사용자 지침 + 원칙 2)*
- [ ] **보조 용언** 중 불필요한 것 제거. (예: "~해 보다", "~하고 있다"에서 군더더기) *(원칙 1)*
- [ ] **불필요한 수식어**(관형어·부사어) 제거. *(원칙 3)*
- [ ] **접미사 '-들'** 등 문맥상 없어도 되는 복수 표지 생략. *(원칙 4)*
- [ ] **지시어**('이·그·이러한')의 대상이 분명하고 적합한지 점검. *(원칙 5)*

#### 중복 없애기

- [ ] **동어 중복** — 같은 단어 반복(의도적 강조가 아니면) 정리. *(원칙 6)*
- [ ] **동의 중복(겹말)** — 같은 뜻이 겹치는 표현 제거. (예: '미리 예상', '역전 앞', '남은 여생') *(원칙 7·8)*
- [ ] **같은 문법 요소 중복** — 조사·어미의 반복으로 흐름이 끊기지 않게 정리. *(원칙 9)*

#### 간결·우리말

- [ ] **의존 명사 '것' 줄이기.** '~하는 것이다/~라는 것' 남용을 평서문으로. *(원칙 10)*
- [ ] **불필요한 표현** 제거로 간결화. *(원칙 11)*
- [ ] **관형격 조사 '의' 줄이기.** *(원칙 12)*

#### 검출 보조 (참고용, 삭제는 문맥 판단)

편별로 후보를 기계적으로 셀 때 쓰는 표지. 수치는 참고일 뿐, 위반 여부는 문맥으로 판단한다.

```bash
# 문두 접속어
grep -oE '(^|[.」”"] ?)(하지만|그리고|그런데|따라서|그러나|그래서|그러니|그러면)' <파일> | wc -l
# 의존명사 '것'
grep -oE '것(이다|이|을|은|과|도|만|의|들)?' <파일> | wc -l
# 복수 '-들'
grep -oE '[가-힣]들' <파일> | wc -l
```

### 6. 리뷰 인계

#### 공통 필수

- [ ] 원문 또는 승인 자료, 포스트별 스펙, 구조 예외와 사유, provenance 분류를 인계한다.
- [ ] 사실과 기술 주장에 대한 출처, 실행한 검증과 결과, 실행하지 못한 검증과 이유를 인계한다.
- [ ] 증명, 코드, SVG, 계산 예시, 복잡도 모듈의 적용 결과를 각각 기록한다. 쓰지 않은 모듈도 생략하지 말고 `N/A — 해당 요소 없음` 또는 구체적인 미적용 사유를 남긴다.
- [ ] 원문의 의도와 달라질 수 있는 수정, 남은 불확실성, 리뷰어가 판정해야 할 항목을 분리해 적는다.
- [ ] 게시 본문에는 provenance 라벨을 넣지 않고, 해당 정보는 포스트별 스펙 또는 리뷰 인계물에만 둔다.

## 완료 기준 (편당)

- 1단계부터 6단계까지 각 단계의 공통 필수를 확인했고, 해당하는 조건부 모듈은 근거와 검증 결과를, 해당 없는 모듈은 `N/A — 해당 요소 없음`을 리뷰 인계에 남겼다.
- provenance와, 구조 기본값에서 벗어난 부분의 사유를 포스트별 스펙 또는 리뷰 인계물로 넘겼다.
- 작성자는 사실·기술 정확성과 증명 타당성을 자체 인증하지 않고 근거·재현 절차·남은 불확실성을 리뷰어에게 넘겼다.
- 게시 본문에 비공개 원천(Notion 원문·강의 노트)을 가리키는 서술이 남지 않는다. 걷어낸 자리에서 논증 단계나 조건이 함께 사라지지 않았다.
- 문두 접속어·겹말·군더더기·불필요한 '것/의/-들'이 꼭 필요한 곳에만 남는다.
- 의미·수식·코드는 그대로이고 직관 설명의 자연스러움을 해치지 않는다.
- `npm run build` 통과.

## 인용과 귀속 주의

- **Hemingway 오인용**: “Write drunk, edit sober.”와 “There is nothing to writing. All you do is sit down at a typewriter and bleed.”는 검증 가능한 1차 출처 없이 Hemingway의 말로 인용하지 않는다. 이 문서의 규칙을 Hemingway의 말로 바꾸어 소개하지 않는다.
- **“Kill your darlings”**: 여러 작가에게 귀속되는 통용 문구다. 특정 작가의 직접 인용으로 쓰지 말고, 필요하면 출처와 정확한 원문을 별도로 확인한다.
- **Strunk와 White 구분**: “Omit needless words.”는 E. B. White가 참여하기 전 William Strunk Jr.의 단독 저술 판본에 나온다. 후대의 *The Elements of Style* 전체를 말할 때만 Strunk와 E. B. White를 함께 적는다.
- **부사 절대 금지 금지**: 작가의 장르별 선호나 조건부 조언을 모든 글의 법칙으로 만들지 않는다. 부사, 수동태, 긴 문장은 뜻과 논증을 흐릴 때 고치며 기계적으로 삭제하지 않는다.
